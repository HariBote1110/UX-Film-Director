

根本原因は、**f32/f64 の桁数差ではなく、`pow`/`powf` の実装依存な最終ラウンド差**です。

## 結論

TS の

```ts
1 - Math.pow(1 - t, 3)
```

と Rust の

```rust
1.0 - (1.0 - t).powf(3.0)
```

は、数学的には同じですが、浮動小数点では**必ずしも bit 同一の結果を返しません**。

`Math.pow` も `powf` も、内部で使うライブラリ実装、アルゴリズム、丸め方法が環境・ランタイム・ビルドによって異なることがあります。特に今回は `x^3` という **指数が整数のべき乗** なので、実装によっては次のような別々の計算経路を取ることがあります。

```text
x * x * x
```

のように乗算展開する実装と、

```text
exp(3.0 * log(x))
```

のように汎用 `pow` を呼ぶ実装、あるいは別の多項式近似・libm 実装を使う場合です。

これらは数学的には等価ですが、浮動小数点の丸めは結合則・分配則が厳密に成り立つわけではないため、**最終的に隣接する 2 つの f64 のどちらかに丸めるか**が実装によって変わります。その結果として、transform 値の末尾 1 ulp だけが異なる、という事象になります。

つまり今回の根本原因は：

> **TS ランタイムの `Math.pow` と Rust 実装が呼ぶ `powf`/libm の `pow` が、同じ f64 入力で最終 f64 へ丸めた結果を 1 ulp だけ異ならせたこと。**

であり、`f32` と `f64` のような有効桁数差ではありません。

---

## なぜ「f32/f64 精度差」ではないのか

両側とも f64、つまり IEEE 754 double で計算しているので、桁数差による系統的な誤差、例えば約 `1e-7` 程度の差が出るようなものではありません。

今回の差は「末尾 1 ulp」だけです。これは f64 の最下位ビット、つまり**隣接する 2 つの表現可能値のどちらを選ぶか**という差です。

f32/f64 差なら、より大きな系統的なズレや、多くのフレームで安定して差が出る傾向があります。今回のように 58 フレーム中 3 フレームだけ、しかも 1 ulp だけであるのは、**特定の値で丸め境界に接近したため、実装差が最後のビットとして顕在化した**典型的なパターンです。

---

## なぜ easeOutCubic のフレームでだけ起きるのか

### 1. easeOutCubic は `pow` を通る

```ts
easeOutCubic: (t: number) => 1 - Math.pow(1 - t, 3),
```

この関数は、`1 - t` という連続的に変わる分数を底にして `pow` を使っています。

つまり：

```text
ease = 1 - (1 - t)^3
```

となり、`(1 - t)^3` の評価が transform に影響します。

一方、他のイージングが例えば：

```ts
t
t * t
1 - (1 - t) * (1 - t)
```

のように `+ - * /` のみで済む場合、それらの基本演算は f64 として同じ計算順序・同じ丸め規則なら実行環境をまたいで bit 同一になる傾向が強いです。

したがって、`pow` を使う easeOutCubic のような非線形関数だけが、実装差の影響を受けやすくなります。

---

### 2. `pow` は IEEE 754 の基本演算ではない

加減乗除は、IEEE 754 の丸めモードなどが揃っていれば比較的決定的です。

しかし `pow` は、特殊値を除けば、一般的な「加減乗除」と同じように標準で最終ラウンドが完全に固定された基本演算ではありません。実装が：

```text
x * x * x
```

でも、

```text
exp(y * log(x))
```

でも、あるいは別の多項式近似でも、結果として 1 ulp 程度で収まっていれば許される範囲にある、というのが実態です。

そのため、

```ts
Math.pow(x, 3)
```

と、

```rust
x.powf(3.0)
```

が、同じ `x` でも最終 1 ulp を異ならせる可能性があります。

---

### 3. 58 フレーム中 3 フレームだけ、という理由は「丸め境界」

58 フレームは離散的な `t` の値です。その中のほとんどの値では、TS 側の `Math.pow` と Rust 側の `powf` が同じ f64 に丸まります。

しかし、特定の 3 つの `t` では、

```text
(1 - t)^3
```

の評価結果が、ちょうど隣接する 2 つの f64 の中間付近に落ち、片方の実装は下へ丸め、もう片方は上へ丸め、といったことが起きます。

すると：

```text
1 - pow_result
```

で得られる easing 値の末尾ビットが 1 ulp ずれます。

さらにその easing 値が transform 計算、例えば：

```text
start + delta * eased
```

のような乗算・加算を通じて transform 値に合成される際、多くのフレームではその 1 ulp 差が後の丸めで吸収されます。

しかし、3 フレームだけ transform 値そのものがまた別の丸め境界付近にあり、結果として **transform 値の末尾 1 ulp だけ**として観測された、と考えられます。

---

## `1 - (1 - t)^3` の打ち消しの影響

`easeOutCubic` は：

```text
1 - (1 - t)^3
```

という形になっています。

`1 - t` が 1 に近い、つまり `t` が 0 に近い区間では、`(1 - t)^3` も 1 に近く、その値を 1 から引くと下位桁が失われやすい形になります。

そのため、`pow` の評価結果の最下位ビットが実装によって 1 ulp だけ異なると、その差が easing 値、ひいては transform 値の下位ビットとして残りやすくなります。

これは「数値的に不安定な形」として理解できます。数学的には：

```text
1 - (1 - t)^3
= 3t - 3t^2 + t^3
```

に展開することもできますが、浮動小数点ではこのように形を変えただけでも最終ビットが変わり得ます。つまり重要なのは数学的等価性ではなく、**実際の浮動小数点プログラムとしての計算順序とライブラリ関数の実装**です。

---

## 根本原因の整理

今回の 1 ulp 差の根本原因は以下です。

1. **両側とも f64 だが、`pow` は bit 互換が保証されない関数である。**
2. **TS の `Math.pow(1 - t, 3)` と Rust の `(1.0 - t).powf(3.0)` は、同じ数学式でも内部アルゴリズムが異なる可能性がある。**
3. **指数 3 のべき乗は、乗算展開と汎用 `pow` の結果で最終 f64 の丸めが 1 ulp ずれることがある。**
4. **easeOutCubic はその `pow` 結果を `1 - ...` で使うため、下位ビット差が transform 値に出やすい。**
5. **58 フレームのうち 3 フレームだけ、その `t` 値で pow 結果または transform 合成結果が f64 の丸め境界に近かった。**

したがって、今回の事象は：

> **`Math.pow` と Rust の `powf` の実装差による、`easeOutCubic` の 3 乗評価における 1 ulp 級の丸め差が、特定フレームの transform 値の末尾ビットとして顕在化したもの**

と分析できます。

---

## 実務的な判断

この 1 ulp 差は、f32/f64 のような桁数不足や、論理的な実装ミスというよりは、**非基本演算である `pow` をまたいだ bit 完全一致比較が過剰に厳しすぎる**ために発生しています。

パリティテストとしては、次のいずれかが適切です。

```text
1. 完全一致ではなく 1 ulp 許差で比較する。
2. pow を使わず、x * x * x などの同じ計算順序を TS/Rust で揃える。
3. easing を多項式展開し、双方で同一の浮動小数点演算順序に固定する。
4. fixture は Rust 側で生成するのではなく、参照実装として別の実装、または許差付きの golden 値にする。
```

特に重要なのは、`pow` を含む実装間で **bit 完全一致を期待しない**、ということです。
