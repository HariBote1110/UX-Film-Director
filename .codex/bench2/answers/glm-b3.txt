# 根本原因分析

## 結論（要旨）

1 ulp 差の種は **`pow` そのもの**です。IEEE 754 は「加減乗除・平方根」などの基本演算にしか完全丸め（correct rounding。入力が同じなら出力のビットも一意）を要求しておらず、**`pow` は要求対象外**です。そのため：

- TS の `Math.pow` は **JS エンジンに同梱された実装**（V8/Node では fdlibm 由来の pow の移植。`**` 演算子も同じ）
- Rust の `(1.0 - t).powf(3.0)` は `llvm.pow.f64` 経由で **実行環境のシステム libm の `pow`**（glibc / musl / libSystem / ucrt で実体が異なる）

という「別々の実装」を通っており、数学値 `(1-t)^3` が隣接 2 個の f64 の丸め中点に極めて近い入力では、最後の丸め先（最下位 1 ビット）が合法的に割れます。これが 1 ulp 差の起源で、**どちらも不正確なわけではなく、仕様上許された差**です。

## なぜ easeOutCubic のフレームでだけ起きるのか

**パイプライン全体で「完全丸めが保証されていない演算」を使っている箇所が、この 1 点だけだから**です。

- t の導出（除算）、他のイージング（多くは `t*t*x` 型の乗算多項式、あるいは sqrt）、transform の合成（線形補間・行列）は、すべて IEEE 754 が完全丸めを保証する基本演算のみ。完全丸め演算は「入力ビットが同一なら出力ビットも同一」という決定的な写像なので、TS と Rust で差が出る余地がない。
- 一方 `easeOutCubic` の式 `1 − (1−t)^3` は、式中の「3乗」を `Math.pow` / `powf` で書いており、**ここが唯一 pow を呼ぶ箇所**。差が出うる場所はここしかない →「差が出た 3 フレームがすべて easeOutCubic」という観測と完全に整合します。
- 補足：`easeInCubic` が差を出さないのは `t*t*t`（乗算ベース）で書けるからです。なお `Math.pow(x, 3)` と `x*x*x` は一致しない入力が存在する点も重要（後述）。
- 差が「潰れずに」伝わる理由：`v = pow(1-t, 3)` に 1 ulp 差があると、`1 − v` 以降の演算も正確丸めなので差は決定的に運ばれます。特に `v ≥ 0.5`（t ≤ 1−∛0.5 ≈ 0.21）では Sterbenz 補題により `1−v` が誤差ゼロで正確に計算されるため、pow の差分が途中の丸めで吸収されず **そのまま透過**します。さらに「1 に近い値からの減算」という桁打ち落とし構造が、pow の絶対誤差（〜1e-16）を ease 値に対して相対的に増幅し、最終 transform の末尾 1 ulp として可視化します。

## なぜ 58 フレーム中 3 フレームだけなのか

- t はフレーム数で量子化された有限集合で、pow の 2 実装の丸めが割れるのは「真値が丸め境界に極近い」稀な入力だけです。大多数の入力では両実装は同一ビットを返すため、不一致は少数フレームに限られる。
- pow が 1 ulp 違っても、下流の transform 係数倍・加算の正確丸めで差が吸収（0 ulp に潰れる）こともあり、「境界割れ ＋ 吸収されず伝播」の両方を満たしたフレームだけが最終値の 1 ulp として観測される。
- 副次的裏付け：失敗するフレームの集合は libm のバージョン・ターゲット（glibc か musl か、OS 何か）や Node のバージョンで変わり得ます。環境によって失敗フレームが入れ替わる現象があれば、この診断の確度はほぼ確定です。

## 検討したが排除した仮説

- **f32/f64 精度差**：両側 f64 なので不成立（前提から除外）。
- **t の導出差（秒/フレーム、除算順序）**：除算は完全丸めでビット一致。仮に t が違えば easeOutCubic 以外のイージングでも差が出るはずだが、一致している。
- **FMA 自動融合・x87 拡張精度**：コードに `mul_add` がなく、LLVM は fast-math なしでは浮動小数演算を再結合しない。x87 は x86_64 ターゲットでは非該当。
- **JIT の定数畳み込み・最適化差**：V8 は Math 系数値関数のティア間一貫性を保つ設計であり、本件は「エンジン同梱 libm vs システム libm」という別の問題。
- **JSON シリアライズ差**：serde_json も JS も最短ラウンドトリップ表現を使い、ビット同一なら文字列も同一。差は実在する値差。

## 検証手順（原因の確定方法）

1. 失敗した 3 フレームの t を抽出し、単に `Math.pow(1-t, 3)` と `(1.0-t).powf(3.0)` だけを比較する → この 3 入力だけで丁度 1 ulp 違うはず。
2. Rust 側を musl ターゲット（fdlibm 系、V8 と同系統）でビルドし直す → 失敗が消える/変わる。
3. 双方を乗算ベースに書き換える → 全フレーム一致。

## 対処

**根治（ビット再現性を取り戻す）**：pow をやめ、両側で同一の四則演算に落とす。乗算・減算は完全丸めなので、同じ演算順序なら常にビット一致します。

```ts
// TS
easeOutCubic: (t: number) => { const u = 1 - t; return 1 - u * u * u; },
```
```rust
// Rust
fn ease_out_cubic(t: f64) -> f64 { let u = 1.0 - t; 1.0 - u * u * u }
```

注意：**両側を同時に置換すること**。片側だけ乗算にすると `Math.pow(x,3) ≠ x*x*x` となる入力が別途生まれ、むしろ差の温床になります（Rust の `powi(3)` は `x*x*x` 展開なので TS 側と揃う）。

**緩和**：パリティ判定に ulp 許容誤差（例： ±2 ulp）を導入する。pow/exp/log/sin のような完全丸めが要求されない関数を跨ぐ処理について、言語間の完全ビット一致を要求するのはテスト設計として過剰であり、libm 起源の差は既知のノイズとして扱うのが定石です。あるいは pow 相当を musl / SLEEF / crlibm など同一実装で両言語から使う方針もあり得ます。

## 一言で言えば

「1 ulp の種」は `Math.pow`（エンジン同梱の fdlibm 系）と `powf`（システム libm）という**別々の pow 実装の最終丸めの 1 ビット差**。パイプライン内で完うに丸めが保証されない非確定要素を使っている箇所が easeOutCubic 内の pow 一箇所だけなので差はそこにしか現れず、「真値が丸め境界に近い稀な t」でだけ種が生じ、`1 − (1−t)^3` の減算構造（Sterbenz による透過性と桁打ち落としによる増幅）によって消されずに最終 transform の末尾 1 ulp まで届いた——これが本件の全体像です。
