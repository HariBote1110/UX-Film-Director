# 根本原因の分析

## 結論

根本原因は、**`pow`（TS: `Math.pow` / Rust: `f64::powf`）の最終丸めが実装間で一致する保証がなく、実際に一致していないこと**である。

`1 - (1-t)^3` という式は両側で数値的にも構造的にも同一だが、その評価過程のうち IEEE 754 で結果が一意に定まるのは基本演算（`+ - * /`）だけである。`pow` は IEEE 754 の必須演算ではなく正しい丸めが要求されず、ECMAScript 仕様も `Math.pow` を implementation-approximated（実装近似値の返却を要求するのみ）と規定している。TS 側は V8 内蔵の実装（fdlibm 由来）、Rust 側は `llvm.pow` 経由でターゲットの libm（glibc / macOS libm / UCRT / wasm ターゲットなら musl 由来の libm crate）に委譲されており、**この 2 つの pow 実装が同一入力に対して隣接する double を返すケースが存在する**。

## 差分の伝播チェーン

1. `t` の算出： 差が easeOutCubic フレームに限定されていることから、フレーム時刻の計算と補間式自体は bit 一致と推断できる（後述のとおり基本演算は決定的）。
2. `u = 1 - t`: 減算は IEEE 754 で正しく丸められるため **bit 一致**。
3. `u^3`: **ここが分岐点**。真値 `(1-t)^3` が隣接 2 つの double の丸め境界の極近傍にあると、拡張精度の中間値が境界のどちら側に落ちるかが実装のアルゴリズム・内部精度次第で決まり、V8 と libm が逆側に丸める → **1 ulp 差**。
4. `1 - u^3`: 再丸めが入るが、差は「打ち消される」か「1 ulp のまま残る」かのどちらか（cube ≥ 0.5 の範囲なら Sterbenz の定理により減算は誤差ゼロで差がそのまま伝播）。増幅はしない。
5. transform への補間： eased 値の 1 ulp 差が最終 transform 値の末尾 1 ulp として現れる。

## なぜ「ちょうど 1 ulp」なのか

pow は内部を 106〜128 ビット規模の拡張精度で計算し、最後に 1 回だけ 64 ビットへ丸める。両実装とも誤差 1 ulp 未満に抑えた高品質実装であるため、同一入力への返値は「真値に最も近い 2 つの double のどちらか」に限られる。結果、食い違い得る幅の上限は隣接 2 値の間隔、すなわち **1 ulp** であり、観測事実と完全に整合する。片方の実装が粗ければ差は 2 ulp 以上になり得たが、そうはなっていない。

## なぜ easeOutCubic のフレームだけか

- 四則演算のみで構成される easing（linear、quad 系など）は、入力ビットと演算順序が同じなら言語・OS・コンパイラを問わず **bit-exact** に一致する（IEEE 754 が正しい丸めを規定するため）。したがって差は原理的に出ない。
- easeOutCubic だけが式に `pow` を含むため、ここだけで「実装依存の丸め」という非決定性のノックアウトゾーンに入る。
- 58 フレーム中 3 フレームのみ差が出たのは、その 3 つの `t` における `(1-t)^3` の真値が偶然丸め境界の極近傍にあっただけである。境界から離れた入力では両実装とも同じ double に丸めるため差は出ない。頻度としても自然。
- 注意： 他の easing も将来 `pow` を使う実装（`easeInOutExpo` 等）に差し替われば、同種の差分はどこででも起こり得る。今回は「pow を使い、かつ境界を踏んだ」フレームがたまたま 3 つあっただけ。

## 補強： 原因は「TS と Rust の差」ではなく「pow の丸め」そのもの

double の立方を正しく丸めるには最大約 159 ビット（53×3）の精度が必要で、一般の pow は log/exp 経路の近似でこれを行わない。そのため**同じ処理系内であっても** `Math.pow(x, 3)` と `x*x*x`、Rust なら `powf(3.0)` と `powi(3)`/乗算が 1 ulp 食い違い得る。つまり片側だけ pow を乗算に置き換えても一致はしない（一致させるには両側を同一の演算列に揃える必要がある）。本件の本質は言語差ではなく「pow には丸めの規格上の保証がない」ことである。

## 検討・除外した他の仮説

- **f32 の混入**： 仮に介在していれば f64 空間での差は 1 ulp より大きく、かつ easeOutCubic 以外の全演算にも波及するはず。観測（1 ulp・easeOutCubic のみ）と不合。
- **FMA 縮約**： Rust は既定で浮動小数縮約を行わず、JS エンジンも融合しない。仮にあっても四則演算のみの easing まで差が出るはず。
- **x87 拡張精度**： 現行の両環境とも SSE2 以降で f64 丸めは即時に行われる。
- **式構造・演算順序の差**： 両式は `1 - (1-t)^3` として同一。
- **JSON の丸め**： 最短丸め再帰シリアライズ（Ryu/Grisu 系）と JS の正しく丸めるパースは f64 を可逆に往復させるため発生源になり得ない。ただし比較を「文字列一致」にしている場合、1 ulp 差が文字列差として可視化されるという表示上の話はあり得る。

## 切り分けと対策

- **切り分け**: 差分フレームの `t` について、両側で `1 - t` のビットを比較する（TS: `DataView` + `getBigUint64`、Rust: `f64::to_bits()`）。`u` が一致して `u^3` だけ異なれば、発散点が pow であることが確定する。
- **本質対応**: 整数指数のべきを両側で同一の乗算列に統一する。TS: `1 - u*u*u`、Rust: `1.0 - u*u*u`（`u = 1.0 - t`）。`powi(3)` でも概ね同等だが、内部の乗算順序に依存しない明示乗算が確実。これで bit-exact 一致する。
- **受入対応**: pow/exp/sin 等を含む式については bit-exact を要求せず、パリティテストを「ULP 距離 ≤ 1 の許容比較」に変更する。fixture の生成を単一実装に寄せ、比較側を許容付き照合にする運用も有効。
- **設計原則**： 「IEEE 754 で一意に定まる演算のみが cross-language の bit-exact を期待でき、pow・exp・三角関数は実装依存」という前提をテスト設計の初期条件に置くこと。
