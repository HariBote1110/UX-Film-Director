この 1 ulp 差の根本原因は、**「`Math.pow`（TypeScript）と `powf`（Rust）はどちらも IEEE 754 binary64 だが、内部的な `x^y` の実装が言語・ライブラリによって異なり、正確に同じビット列を返す保証がない」**ことです。

## なぜ 1 ulp 差が生じるのか

1. `easeOutCubic` は
   ```
   1 - (1 - t)^3
   ```
   を計算します。ここで `(1 - t)^3` は実数としては同じ値でも、浮動小数点で計算するとどのように近似的に実装されているかによって末尾ビットが変わることがあります。

2. `Math.pow` と `powf` は多くの実装で `exp(y * log(x))` 系あるいは専用の近似多項式で計算されます。これらの算法は仕様上 1 ulp 以内の誤差まで許容されることが多く、最終的な丸め方向がプラットフォーム・ライブラリごとに異なることがあります。

3. 特に指数が `3.0` という整数値の場合、実装によっては
   * 素直に `x * x * x` とするケース
   * 一般の実数指数と同じ `log/exp` 系のパスを使うケース
   
   があります。パスが異なると、乗算回数や中間丸めが変わり、結果が 1 ulp だけずれることがあります。

4. TypeScript（V8/Node/Browser の `Math.pow`）と Rust（`libm` や LLVM 由来の `powf`）では、たとえ同じ `f64` 型でもこの部分の算法や丸めが一致しないため、 rare な入力値で 1 ulp だけ異なる値を返し、その差が
   ```
   1 - ...
   ```
   を経て `transform` の値の末尾 1 ulp 差として現れています。

## なぜ他のフレームや他のイージングでは起きないのか

* 多くのイージング関数（例えば `t * t * t` など）は **`*` 演算のみ**で実装されており、`*` は IEEE 754 規格でほぼ決定的に定まった丸めを持つため、TypeScript と Rust でビット一致しやすいです。
* 一方 `easeOutCubic` はこのテスト対象の中で **唯一 `Math.pow` / `powf` を使う指数計算に依存している**ため、`x^3` の実装差が表出するのはこの関数に限られます。
* 58 フレーム中 3 フレームだけ差が出たのは、残りの `t` 値では両方の `pow` 実装が偶然同じ丸め結果を返したが、特定の 3 フレームの `t` 値では丸め方向が分岐したためです。

## 対策案

`pow`/`powf` の実装差を避けるには、整数指数 3 を用いる箇所を自前の乗算に置き換えます。

```ts
// TS
easeOutCubic: (t: number) => {
  const u = 1 - t;
  return 1 - u * u * u;
},
```

```rust
// Rust
fn ease_out_cubic(t: f64) -> f64 {
    let u = 1.0 - t;
    1.0 - u * u * u
}
```

これにより、指数関数ライブラリの丸め差ではなく決定論的な乗算のみになり、1 ulp 差は解消されます。
