# psd_fast.rs レイヤー並列デコードのスレッド数スケーリング

## 目的・仮説（棄却条件込み）

`native-psd-fast-single-thread.md` により、ネイティブ単一スレッド版
`parse_psd_fast` は median ≈ 219〜224ms（ag-psd (b) 405ms を約46%短縮）
まで到達済み。この 220ms の内訳（メタデータ解析 vs レイヤーごとの
チャンネル圧縮解除）を確認したうえで、レイヤー単位のデコードは互いに
独立（各レイヤーが自分専用の出力 `Vec<u8>` に書き込むのみで共有状態が
無い）という前提のもと、スレッドプールで並列化した場合のスケーリング
を計測する。

**先行知見への警戒**: `markdown/PSD_WASM_Challenge.md` に記録されている
とおり、ブラウザの 8-Worker 並列化は SharedArrayBuffer 上のランダム
アクセスによるキャッシュスラッシングで壊滅的に負けた前例がある。
ネイティブスレッド + 独立した出力バッファはこの病理を回避できる
はずだが、**推測せず計測する**。

**仮説**: 220ms の大半はレイヤーごとの圧縮解除フェーズが占めており、
レイヤーは独立しているため、デコードループをスレッドプールで並列化
すればコア数のかなりの割合までスケールする。8〜12 スレッドで
median ≈ 60ms 以下を期待する。

**棄却条件**: スピードアップが 2 倍未満で頭打ちになる場合、この
ワークロードはメモリ帯域幅律速（または直列区間支配）であり、スレッド
数を増やす方向はこれ以上のレバーにならない、と記録して棄却する。

## 手順

### Step 1: フェーズ分割の追加（並列化前のベースライン内訳確認）

`vm_tuning_research/tools/psd-native-bench/src/psd_fast.rs` に
`parse_psd_fast_instrumented(bytes, num_threads: Option<usize>)` を追加し、
以下 3 フェーズの `Instant` 計測を行うようにした（`PhaseTimings` 構造体）。
既存 `parse_psd_fast`（無改変、「オリジナルの直列パス」として温存）とは
別の新規関数であり、既存の単一スレッド計測結果に影響しない。

- `parse_records_ms`: レイヤーレコード（座標・可視性・グループ構造・
  チャンネル長）のメタデータ解析のみ。ピクセルバイトには一切触れない。
- `decode_layers_ms`: 各レイヤーのバイト範囲事前計算（軽量、伸長なし）
  + チャンネル圧縮解除（PackBits/ZIP/Raw）+ RGBA インターリーブ。
- `tree_build_ms`: グループツリー再構築 + pre-order フラット化。

VM 上で `pool0`（後述、プールなしで範囲事前計算パイプラインのみを通す
直列パス）を 15 回実行（先頭3回ウォームアップ破棄、有効 n=12）した
結果:

| フェーズ | median (ms) | 全体に占める割合 |
|---|---|---|
| parse_records | 0.044 | 0.02% |
| decode_layers | 217.507 | 99.96% |
| tree_build | 0.025 | 0.01% |
| **overall** | **217.588** | 100% |

→ **220ms のほぼ全量（99.96%）がレイヤーごとの圧縮解除フェーズに
集中**しており、メタデータ解析とツリー構築は無視できるコスト
（合計 0.07ms 未満）。仮説の前提（「220ms の大半はデコードフェーズ」）
はこの時点で確認済み。並列化の対象を `decode_layers` フェーズのみに
絞ることが妥当と判断した。

### Step 2: 並列デコードモードの実装

`vm_tuning_research/tools/psd-native-bench/` に以下を追加:

- 依存クレート追加: `rayon = "1"`（解決バージョン `rayon 1.12.0`、
  `rayon-core 1.13.0`。`Cargo.lock` に記録済み）。選定理由: スレッド数
  を指定できるスコープ付きスレッドプール
  （`ThreadPoolBuilder::num_threads(n).build()`）が標準で用意されており、
  `std::thread` で手動チャンク分割するより実装・保守が簡単なため。
- `psd_fast.rs`:
  - `compute_leaf_ranges()`: 各リーフレイヤーの「ファイル内バイト範囲」
    を、実際の伸長を行わずカーソル移動のみで事前計算する関数
    （既知の `ChannelInfo::data_len` を合算するだけなので軽量）。
  - `decode_from_range()`: `bytes` 全体から `&bytes[start..end]` を
    サブスライスして独立した `Cursor` を作り、既存の
    `decode_layer_rgba()`（無改変）をそのまま呼ぶ。各レイヤーの入力
    スライスと出力 `Vec<u8>` が完全に独立するため、これがそのまま
    スレッド間で共有状態なしに並列実行できる単位になる。
  - `parse_psd_fast_instrumented(bytes, num_threads: Option<usize>)`:
    - `None`: プールを作らず呼び出しスレッドで直列デコード（＝
      `pool0` モード。範囲事前計算パイプラインは通るが並列実行はしない）。
    - `Some(n)`: `rayon::ThreadPoolBuilder::new().num_threads(n).build()`
      でプールを作り、`records.par_iter().zip(ranges.par_iter())` で
      並列デコード。**`n = 1` も意図的にこのプール経由のコードパスを
      通す**（プールのオーバーヘッドを "serial"/`pool0` から分離して
      見えるようにするため。指示どおり）。
  - 既存 `parse_psd_fast`（単一スレッド・単一パスの直列実装）は**無改変**
    のまま "serial" モードとして残置。ツリー構築ロジック（`TreeNode`
    enum・`flatten`）はモジュールスコープの共有関数
    `build_layer_tree()` / `flatten()` に括り出したが、処理内容・呼び出し
    順は元のまま（挙動非破壊のリファクタ）。
- `main.rs`: CLI 第3引数でモード切替（`serial` / `pool0` /
  `<正の整数N>`）。各反復ごとに overall とフェーズ内訳（`parse`/
  `decode`/`tree`）の両方を出力するよう変更。

### Step 3: 正しさ検証

各モード（`serial`, `pool0`, `1, 2, 4, 6, 8, 12`）で
`total_decoded_rgba_bytes = 345168656` かつ `layer_count = 171` が
一致することを、ローカル（サンプルスモーク、6反復）と VM 本番実行
（各 4〜15 反復）の両方で確認した。**全モード・全実行で完全一致**
（不一致ゼロ）。

### Step 4: スケーリング計測プロトコル

VM 上、`~/psd-bench/psd-native-bench/target/release/psd-native-bench`
（`opt-level=3, lto=fat, codegen-units=1, panic=abort` の release
ビルド、VM 上ビルド時間 11.46秒）で、モード
`serial, pool0, 1, 2, 4, 6, 8, 12` を 1 セットとし、各モード 15 回
実行（先頭3回ウォームアップ破棄、有効 n=12）。これを 2 セット、
モード列挙順を固定したまま連続実行して interleave した（セット1全
モード → セット2全モード）。ログ全文: VM 上
`~/psd-bench/results/scaling_log.txt`。

### スピードアップとスケーリング効率

基準値: `serial` の 2 セット median 平均 = 217.167ms。
スピードアップ = 217.167 / (当該モードの 2 セット median 平均)。
スケーリング効率 = スピードアップ ÷ N × 100%（N=1 は基準として計算対象外、
N=0相当の pool0 も対象外）。

| モード | 2セット median 平均 (ms) | スピードアップ | スケーリング効率 |
|---|---|---|---|
| serial（基準） | 217.167 | 1.00x | — |
| pool0 | 220.481 | 0.98x | — |
| N=1 | 247.812 | **0.88x（悪化）** | — |
| N=2 | 190.514 | 1.14x | 57.0% |
| N=4 | 124.235 | 1.75x | 43.7% |
| N=6 | 130.421 | 1.67x | 27.8% |
| N=8 | 106.067 | 2.05x | 25.6% |
| N=12 | 108.014 | 2.01x | 16.8% |

観察点:

- **N=8 で頭打ち**。N=8 → N=12 でスピードアップはむしろ微減
  （2.05x → 2.01x）。N=12 まで増やしても改善しない。
- **N=6 が N=4 より遅い**（非単調）。12 vCPU 環境の P/E コア非対称
  トポロジ（環境節参照）や、ホスト側の他 VM とのスケジューリング
  競合が原因の可能性があるが、本実験の範囲では原因切り分けは未実施。
- **N=1（プール経由）は serial より 14% 遅い**。`ThreadPoolBuilder::build()`
  を計測対象の反復ごとに毎回呼んでいるため（本ベンチの設計上、1回の
  `parse_psd_fast_instrumented` 呼び出しの中でプールを都度構築している）、
  プール生成コストが 1 レイヤー分の恩恵を上回っている。本番想定では
  プールをプロセス起動時に1回だけ構築して使い回せばこのオーバーヘッドは
  消えるはずだが、**今回のベンチの計測条件では「N=1 は素の直列より遅い」
  という結果を正直に記録する**（プール毎回構築という実装選択の副作用
  であり、並列化そのものの限界とは別の要因）。
- `pool0`（プールなし・範囲事前計算パイプラインのみ）は `serial`
  とほぼ同水準（220.5ms vs 217.2ms、差は VM ノイズレベル内）。
  範囲事前計算パス自体の追加コストはごくわずか。

### 比較サマリ（対 ag-psd、対 WASM_Challenge）

| 実装 | median (ms) | 対 ag-psd (b) 405ms |
|---|---|---|
| ag-psd (b) skipComposite+skipThumbnail | 404.95〜405.77 | 基準 |
| psd_fast.rs ネイティブ単一スレッド（既存記録） | 219.40〜223.59 | 約1.8倍速 |
| **本計測: psd_fast.rs ネイティブ + N=8 スレッドプール** | **103.6〜108.5** | **約 3.8〜3.9倍速（約 73% 短縮）** |
| （参考）`PSD_WASM_Challenge.md`: ブラウザ 8-Worker 並列（WASM） | 個別 Worker 278〜468ms（1レイヤー ~93ms、SharedArrayBuffer ランダムアクセスでキャッシュスラッシングし逆に悪化） | 並列化が**逆効果**だった前例 |

対比: ブラウザ 8-Worker 並列は SharedArrayBuffer 上のランダムアクセス
パターンがキャッシュラインを汚染し、並列化してもスループットが
向上しないどころか悪化した（`PSD_WASM_Challenge.md` 67-91行）。
本計測（ネイティブスレッド + 各レイヤー独立の出力 `Vec<u8>`、
`&bytes[start..end]` の読み取り専用サブスライス）はその病理は
再現しなかった（N=8 で確かに約2倍まで速くなっている）が、
**期待した「8〜12スレッドでほぼ線形にスケールする」水準には遠く
届かず、N=8 以降で頭打ちになった**という点で、「並列化すれば
自動的に大幅に速くなる」という楽観は同様に否定された。

## 結論（仮説の採否）

**仮説は棄却。**

- 期待値（8〜12スレッドで median ≦ 約60ms）に対し、実測は
  N=8 で 103.6〜108.5ms、N=12 で 103.2〜108.1ms。目標の**約1.7〜1.8倍
  遅い**。
- 棄却条件（「スピードアップが2倍未満で頭打ち」）についても、実測の
  頭打ち水準はスピードアップ約2.0〜2.05倍とほぼ境界線上で、明確に
  それを上回ってはいない。N=8 から N=12 へコア数を1.5倍に増やしても
  スピードアップは向上せず（むしろ微減）、これは「スレッド数を
  増やす方向はこれ以上のレバーにならない」という棄却条件の記述と
  整合する。
- Step 1 のフェーズ内訳で確認したとおり `decode_layers` フェーズが
  全体の99.96%を占め、かつレイヤー間に共有状態はない設計
  （`decode_from_range` は読み取り専用サブスライス→独立
  `Vec<u8>` 出力）にもかかわらずこの頭打ちが起きている。171
  レイヤー・29.74MB の PSD を約9.1GiB空きメモリ上でデコードする
  ワークロードは、CPU 演算（PackBits/ZIP 展開）よりも
  **メモリ帯域幅（メインメモリ⇔各コアのデータ移動）に律速されて
  いる可能性が高い**、という仮説の棄却条件に記載した代替説明と
  整合する結果になった。VM の 12 vCPU が単一 NUMA ノードに乗っており
  P/E コア非対称トポロジがホストから見えない状態（環境節参照）である
  ことも、単純なコア数増加が線形スケールに直結しない一因として
  考えられる。
- とはいえ「並列化は無意味」ではない。N=8 で約2倍のスピードアップ
  （217ms → 106ms）は実用上意味があり、ag-psd 405ms に対しては
  約3.8〜3.9倍速（約73%短縮）まで到達した。ブラウザ8-Worker並列が
  逆効果だった前例と比べれば、ネイティブスレッド + 独立出力バッファ
  という設計判断そのものは有効だったと言える。ただし「仮説として
  掲げた60ms以下」には届かず、**この実験が問うた仮説（コア数の
  かなりの割合までスケールする）としては棄却**する。

## 次の一手

- メモリ帯域幅律速かどうかを直接確認する追加実験: `perf stat` 等で
  L2/L3 キャッシュミス率・メモリ帯域使用率を N=1/4/8/12 で比較する。
  本実験では perf 系ツールの導入・計測を行っておらず、「帯域幅律速」
  は状況証拠（頭打ちパターン + 199.96%がデコードフェーズという事実）
  からの推定にとどまる。
- N=6 が N=4 より遅い非単調性の原因切り分け（VM ホスト側の他プロセス
  競合か、P/E コア的非対称マッピングか）は未検証。`taskset`/`numactl`
  でコア固定した場合に再現するか確認する余地がある。
- 本番へ再実装する場合、スレッドプールはプロセス起動時に1回だけ構築
  して使い回す設計にすべき（本ベンチのように呼び出しごとに
  `ThreadPoolBuilder::build()` するとN=1で素の直列より遅くなることを
  確認済み）。この点は `promotion discipline`（research → mainstream
  再実装）で必ず踏まえること。
- N=8 を採用する場合でも、VM の 12 vCPU 全部を専有する構成が本番の
  実行環境（Tauri sidecar 等、ユーザーの実マシン）でも妥当かは別途
  検証が必要（ユーザー機は12 vCPUを持たない可能性が高く、
  `std::thread::available_parallelism()` 等でスレッド数を実行時に
  決定する設計が必須になる）。
- `lto = "thin"` や `codegen-units` デフォルトとの比較、`rayon`
  以外の実装（`std::thread` 手動チャンク分割、work-stealingなし）
  との比較は本実験では未実施（`native-psd-fast-single-thread.md` の
  「次の一手」からも持ち越し）。
