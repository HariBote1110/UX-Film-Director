# メモリピーク比較 — ag-psd (Node) vs native psd_fast (serial / N=8)

## 目的 / 仮説

practical-victory-criteria.md の判定基準 3「メモリピーク」を検証する。

対象 PSD（葵ちゃん.psd, 29.74MB, 171 レイヤー）はデコード後の RGBA 合計が
345,168,656 バイト（約 329MiB）。native psd_fast ベンチはこの全量を
`Vec<u8>` として一括保持し、ag-psd も `useImageData:true` で各レイヤーの
`ImageData`（`Uint8ClampedArray` バッキング）として全量を保持する。
すでに確定した時間計測（ag-psd median ≈ 405ms、native serial ≈ 217ms、
native N=8 ≈ 106ms）は本ノートの対象外——ここはピーク RSS のみを扱う。

**仮説（棄却条件を先に固定する）**：
両実装とも「入力バッファ（約30MB）＋全レイヤー分デコード済みRGBA（約345MB）」
を同時に保持する設計であるため、ピーク RSS は同じオーダー（概ね
400〜500MB 以上）になるはずである。ただし ag-psd は V8 上のオブジェクト
ヘッダ・GC 管理領域・中間文字列/配列アロケーションなどの JS 実行時オーバー
ヘッドを追加で背負うため、native よりも明確に高いピークを示すと予想する。

**棄却条件**：native のピークが ag-psd に対して有意に低くない
（差が 20% 未満）場合、現時点の設計ではメモリは差別化要因になっておらず、
判定基準3の実用的優位性の主張は「将来の遅延/ストリーミングデコード」に
委ねるべきであり、今日の設計を根拠にはできない、と結論する。

## 環境

- environment.md と同一（借用 VM, i5-13400F, Ubuntu 26.04, node v22.22.1,
  rustc/cargo 1.93.1, GPU 無し）
- 対象ファイル: `~/psd-bench/葵ちゃん.psd`（29.74MB, 171 レイヤー,
  デコード後 RGBA 合計 345,168,656 バイト）
- 計測ツール: `/usr/bin/time -v`（"Maximum resident set size" フィールド、kbytes 単位）

## 手順

1. ag-psd 単発計測用に `vm_tuning_research/tools/bench-agpsd-oneshot.mjs`
   を新規作成（既存 `bench-agpsd.mjs` の多反復ループはGC履歴でピークを
   歪めるため、1プロセス=1パースのみ実行して終了するスクリプトを別途用意）。
   `readPsd(ab, { useImageData:true, skipCompositeImageData:true,
   skipThumbnail:true })` を1回だけ呼び、結果を `globalThis` に保持した
   まま終了（GC で即座に回収されてピークが過小評価されるのを防ぐ）。
2. 各構成を `/usr/bin/time -v` でラップして3回ずつ実行：
   - (a) `node bench-agpsd-oneshot.mjs 葵ちゃん.psd`
   - (b) `./psd-native-bench 葵ちゃん.psd 1 serial`
   - (c) `./psd-native-bench 葵ちゃん.psd 1 8`（N=8 rayon プール）
3. ベースライン差分用に `node -e ''` の Maximum resident set size を
   3回計測し、node ランタイム自体の起動コストを分離して併記する
   （簡便のため trivial Rust バイナリのベースラインは省略——native 側は
   既存 `psd-native-bench` バイナリ自体の起動コストが数MB程度と小さく、
   ag-psd 側の Node ランタイム起動コストとの非対称性を明示する目的で
   node 側のみ計測する）。

## 結果

`/usr/bin/time -v` の "Maximum resident set size"（kbytes, 1024 バイト単位）。
各構成 3 回計測、layer_count / total_decoded_rgba_bytes は全構成で一致
（143 は ag-psd 側がグループ層を子孫走査時にカウントしない数え方の差で、
native の 171 とは「葉レイヤー数の数え方」が違うだけ——
`total_decoded_rgba_bytes = 345,168,656` が全構成で完全一致しているため、
デコード対象データ量は同一であることを確認済み）。

| 構成 | run1 (KiB) | run2 (KiB) | run3 (KiB) | median (KiB) | median (MiB) |
|---|---|---|---|---|---|
| (a) ag-psd oneshot (Node) | 475,716 | 475,784 | 475,940 | 475,784 | 464.63 |
| (b) native serial (1 iter) | 375,036 | 375,036 | 374,980 | 375,036 | 366.25 |
| (c) native N=8 (1 iter) | 478,276 | 460,472 | 459,788 | 460,472 | 449.68 |
| node baseline (`node -e ''`) | 57,920 | 57,904 | 57,692 | 57,904 | 56.55 |

差分（ag-psd を基準とした native の低減率）:

| 比較 | 差分 |
|---|---|
| native serial vs ag-psd（生値） | **-21.18%**（有意に低い） |
| native N=8 vs ag-psd（生値） | **-3.22%**（ほぼ同水準） |
| ag-psd（node ランタイム起動コスト分を控除した調整値） | 408.09 MiB |
| native serial vs ag-psd（調整値） | -10.25% |

Rust バイナリ側の起動コストベースラインは計測を省略した（後述「未検証事項」）。

## 結論

**仮説は部分的に採用、部分的に棄却。**

- オーダーが同じ（すべて 350〜480MB 帯）という前提部分は的中——
  「入力+全デコード済みRGBA」を同時保持する設計であることの証左。
- **native serial** は ag-psd に対して生値で 21.18% 低いピークを示し、
  棄却条件（差 20% 未満なら棄却）の閾値をわずかに上回った。
  「native の方が明確に低い」という予想は serial モードでは支持される。
  ただし node ランタイム起動コスト（56.55 MiB）を ag-psd 側から控除した
  調整値で見ると差は 10.25% に縮まり、「JS 実行時オーバーヘッドが主要因」
  という説明の一部は node プロセス自体の固定費であって PSD デコード固有の
  オーバーヘッドではないことが分かる——ag-psd のデコード起因の追加コストは
  見た目ほど大きくない。
- **native N=8（最速構成、median ≈106ms のスループット王者）は棄却条件に
  該当**：ag-psd との差はわずか 3.22% で、実用的な優位性を主張できる水準
  ではない。rayon スレッドプールで 8 レイヤーを並行デコードすると、
  各スレッドが担当レイヤーの中間デコードバッファと出力 RGBA バッファを
  同時に保持するため、瞬間的な生存バッファ数が serial（常に1レイヤー分
  のみ）より増え、ピーク RSS が ag-psd 水準まで押し上がる。
  **速度とメモリピークはこの設計ではトレードオフ関係にある。**

判定基準3（メモリピーク）は、native 実装が「常に」ag-psd を超えるとは
言えない。デフォルト/低メモリ用途の serial モードでは実用的な優位性を
主張できるが、判定基準4（スケーラビリティ）で優位性の根拠としている
N=8 の高速経路では、メモリピークの優位性は実質消失する。
criterion 3 と criterion 4 は現行設計では同時に最良化できていない。

## 次の一手 / 未検証事項

- **遅延/オンデマンドのレイヤーデコード**が criterion 3 と criterion 4 を
  同時に前進させる唯一のレバーになりうる：可視レイヤーやビューポート内
  レイヤーのみを要求時にデコードすれば、(1) 常時保持する RGBA 総量が
  345MB から大幅に縮小し、(2) 並列デコードするレイヤー数の上限も
  ワーキングセットに応じて絞れるため、N=8 のピーク押し上げ問題も同時に
  緩和できる。次の実験候補として、N=8 モードで「同時デコード中のレイヤー
  数」を意図的に制限した際のピーク RSS の変化（フル並列 vs バッチサイズ
  制限）を計測し、速度とメモリのトレードオフ曲線を明らかにするとよい。
- 本ノートでは trivial Rust バイナリのベースライン計測を省略した
  （node 側の起動コストのみ分離）。native 側の起動コストは
  `psd-native-bench` バイナリ自体が数MB程度と想定され、node の
  56.55 MiB という起動コストと比べて非対称に小さいと考えられるが、
  未確認。次回このスケールの差が結論を左右する場面があれば計測すること。
