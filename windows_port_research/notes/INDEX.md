- [w7-attach-cost-mitigation.md](w7-attach-cost-mitigation.md) — **W7既定ON化を妨げる約89秒の初回attach同期ブロックを4案で評価**。Option A（`wgpu::Features::PIPELINE_CACHE`）は`wgpu-hal-25.0.2`のDX12バックエンドが未実装（空スタブ、feature未公開、Vulkan専用）と確定し**棄却**。Option D（DXC最適化フラグ）はwgpu本体を改造しない限りアプリ側から制御不能なため見送り。Option B（非同期attach化）は`attach_native_overlay`が`pub fn`（同期）でElectron main processをブロックしていることをコード読みで確認——presenterフォールバックの既存資産を使い「attach完了まで代替描画→完了後に切替」の状態機械へ再設計すれば根絶可能（Viewport.tsxの13箇所の依存整理を伴う中規模改修）。Option C（lazy pipeline creation）は9本の内訳を実装から列挙（598〜678行のuber-shader4本が支配的、37〜152行の小シェーダ8本前後）——Bgra8UnormSrgb版2本の遅延生成は低リスクな補完策だが、per-pipeline実測は未実施で逆算値（19.2秒)は内部矛盾ありと正直に記録。**推奨: Option B必須（UIブロック根絶はBのみが解決）+ Option Cの一部（Bgra遅延）を並行**（2026-08-22）
- [nv12-pipeline-compile-time.md](nv12-pipeline-compile-time.md) — **[w5-attach-hang.md](w5-attach-hang.md)の続き**: `nv12_composite.wgsl`単体の最小再現ツール（`windows_port_research/tools/nv12-pipeline-repro`）で切り分け。macOS/Metalでは1〜3秒未満で完走（H-C採択）——WGSLの記述自体に欠陥は無い。Windows/DX12では`create_shader_module`（naga変換）は1msと一瞬だが`create_render_pipeline`（Fxcコンパイル）が病的に遅い（H-A採択）。**「nv12固有の問題」という当初の見立ては棄却**（H-B棄却）: nv12版が持たない`solid_composite.wgsl`（598行、YCbCr変換部分を除く共通の"effects tail"のみ）も**104.3秒**かかっており、真因は両シェーダが共有する550行超の"effects tail"自体がwgpu既定コンパイラFxc（wgpu自身が"old, slow and unmaintained"と明記）に対して病的に遅いこと。**nv12はタイムアウト900秒で再実行したところ676.9秒（約11分17秒）で完了することを確認——「無限ループ・デッドロックではなく、有限だが非常に長い時間がかかるコンパイル」だったと確定**（solid比で約6.5倍、行数差はわずか+13%なので非線形な悪化）。`DynamicDxc`はmainpcにdxcompiler.dll/dxil.dllが無く`no adapter`で即失敗、`StaticDxc`(`mach-dxcompiler-rs`静的リンク)はMSVC標準ライブラリのシンボル未解決でリンクエラー。**追記: ユーザー承認のもとDXC（github.com/microsoft/DirectXShaderCompiler v1.9.2607）をmainpcへ実際にダウンロード・導入して再実測**——solid 104.3秒→中央値7.5秒（約13.9倍）、nv12 676.9秒→中央値52.4秒（約12.9倍）。`native-wgpu-renderer/src/lib.rs`に`resolve_dx12_compiler`（DLL両方揃えばDynamicDxc、欠ければFxcへ自動フォールバック、TDDで4件テスト追加）を実装し、DLL配置後`native-overlay/tests/win32_overlay_smoke.rs`をmainpcで`schtasks /it`実行——**`test result: ok. 1 passed; ... finished in 79.09s`で完走を確認**。`markdown/Windows_Port_Plan.md`のPhase 5を★完了とした。electron-builderへのDLL同梱はW1フォローアップとして未着手（2026-08-22）
- [w5-attach-hang.md](w5-attach-hang.md) — **W5 attach スモークテストの「ハング」原因を切り分け**。段階ログ（`eprintln`）を `attach_overlay_window`/`from_hwnd`/`from_surface` に仕込んで実機（mainpc）で再現したところ、`DCompositionCreateDevice`/`CreateTargetForHwnd`/`CreateVisual`/`SetRoot` も `wgpu::Instance::request_adapter`/`request_device` も数秒で正常完了しており、メッセージポンプ不在が原因という当初仮説（H-1・H-2）は**棄却**。実際に進行が止まったのは `NativeWgpuLiveSurfaceRenderer::from_surface` が作る9本の描画パイプラインのうち2本目、`nv12::create_nv12_pipeline_for_format`（シェーダ `shared-renderer/shaders/nv12_composite.wgsl`、678行）。10分間 `Get-Process` の CPU 累計を追跡し、単調増加はしているが完了ログが最後まで出ず、増加率も時間とともに鈍化（他の1本目のパイプラインは598行のシェーダで1分未満）。行数比(+13%)に見合わない所要時間の桁違いの差から、単純な「大きいから遅い」ではなく `nv12_composite.wgsl` 固有の構造（naga→HLSL変換またはDXCコード生成の病的な遅さ）を疑う。次の一手はこのシェーダ単体の最小再現とmacOS(Metal)との比較（2026-08-22）
- [sustained-present.md](sustained-present.md) — **W0: 連続 present を実機で検証し破綻しないと確定**。static/move/resize の全フェーズで、ちらつき（画素不一致）0件・z順逆転0件・acquire失敗0件・Suboptimal 0件。RDP仮想ディスプレイが32HzなのでFifoは33fpsに張り付くが上限ではなく、Immediateでは最悪のresizeでも845fps・frame p99=6.1msで16.67ms予算に桁で余る。`queue.present`+`Commit`は p50 0.15msで、フレームタイムの実体は`get_current_texture`のvsync待ち（p50 30.7ms）＝**UIスレッドで呼んではいけない**。surface reconfigureは連続8,445回で失敗ゼロ。GPU使用率はbaseline 12.4%→static 16.3%で電力は不変だが、RDPデスクトップのノイズが大きく強い主張はできない。**Phase 5 は child window + DirectComposition のまま進めてよい**（VisualFromWndHandle は不要）。実シェーダ負荷・物理60Hzディスプレイ・Chromium自身のfpsは未計測（2026-08-22）
- [electron-real-app-on-windows.md](electron-real-app-on-windows.md) — **Electron 実物で検証**。Rust側を一切ビルドせず `npm install`→`npx tsc`→`npx vite build`→`npx electron .` でアプリが Windows で起動しUIも描画（準対応MVPの「ビルド」「起動」を達成）。overlay は実物の Chromium ウィンドウの上でも per-pixel alpha で正しく合成され、ちらつき・z-order競合は観測されず。クリックは `Chrome_RenderWidgetHostHWND` に素通り。起動ログの `DXC create compiler failed` は**無害**で WebGPU は動く（nvidia/ampere、adapter/device とも取得可）——ただし `navigator.gpu` は secure context でしか生えないので `data:` URL で測ると誤判定する。`npm run build` は POSIX形式のenv代入のため Windows で動かない（2026-08-22）
- [dcomp-crosswindow-and-hittest.md](dcomp-crosswindow-and-hittest.md) — **別ウィンドウ間の透過合成とクリック透過を実機確認**。オーナー付き `WS_POPUP`+`WS_EX_NOREDIRECTIONBITMAP` の overlay が、別ウィンドウである親の内容の上に per-pixel alpha で正しく合成された（画面キャプチャで数値・画像とも一致）。クリック透過は **`WS_EX_TRANSPARENT` だけでは抜けず**、`WM_NCHITTEST` に `HTTRANSPARENT` を返して初めて `WindowFromPoint` が下のウィンドウを返す（macOS の `hitTest:` nil と同じ対処）。macOS の Bug E（wgpu が layer を差し替えるので opaque 再適用が要る）に相当する問題は Windows には無い。RDPで接続しセッションをActiveにすると画面キャプチャが機能する。**Chromium 実物との組み合わせは未検証**（2026-08-22）
- [dcomp-transparent-composite-visual.md](dcomp-transparent-composite-visual.md) — **透過合成の目視確認に成功**。Windows実機で wgpu 30 の composition swapchain に premultiplied alpha で描いた内容が DirectComposition で正しく合成された（完全透明部は下の市松がそのまま、50%部は `src + dst*(1-a)` どおりの (128,128,127)）。macOS の CAMetalLayer + setOpaque:NO + 透明clear と同じ構成が DirectComposition + alpha_mode:PreMultiplied でそのまま成立し、退避策は全て不要と確定。z順は `AddVisual` の参照visualを明示しないと逆転する。切断RDPセッションでは画面キャプチャが全面黒になるため `PrintWindow(PW_RENDERFULLCONTENT)` を使う。**別ウィンドウ間の合成（Electron/Chromium の上に乗せる形）は未確認**（2026-08-22）
- [dx12-alpha-real-hardware.md](dx12-alpha-real-hardware.md) — Windows実機（mainpc / RTX 3070 Ti）で透過を実測。現行 wgpu 0.20 は実機でも `ALPHA_MODES=[Opaque]` で PreMultiplied は configure 失敗（前ノートの読解を追認）。**しかし wgpu 30 では同じ機械・同じ IDCompositionVisual で `[Auto, Inherit, Opaque, PostMultiplied, PreMultiplied]` となり PreMultiplied が通った** ——修正は **wgpu-hal 25.0.2** から入っており、透過不可はプラットフォーム制約ではなく wgpu のバージョン問題と確定（仮説H-2棄却）。wgpu-hal パッチも自前 swapchain も不要。ただし透過が効くのは composition 系 target のみで素の HWND は 30 でも Opaque。SSH 直実行では DirectComposition が E_ACCESSDENIED になるため `schtasks /it` 経由で実行する必要がある（2026-08-22）
- [cametallayer-equivalent-and-alpha.md](cametallayer-equivalent-and-alpha.md) — CAMetalLayer の Windows 相当は IDCompositionVisual で、wgpu 0.20 に `SurfaceTargetUnsafe::CompositionVisual` の入口も既にある（仮説H-2棄却）。**ただし wgpu-hal の dx12 backend が `composite_alpha_modes` を Opaque のみ広告し `map_acomposite_alpha_mode` が `DXGI_ALPHA_MODE_IGNORE` を直返しするため、wgpu 経由では透過 overlay が作れない**（wgpu-hal 24.0.4 でも同様＝バージョン上げでは直らない）。しかも `choose_live_surface_alpha_mode` が Opaque へ黙って fallback するのでエラーにならず無言の見た目バグになる。overlay surface の入口 `from_appkit_view` は macOS 専用、`from_surface` は cfg なしで再利用可能（2026-08-22）
- [current-portability-audit.md](current-portability-audit.md) — `cargo check --target x86_64-pc-windows-msvc` による現状棚卸し。唯一のビルドブロッカーは `shared-memory-spike` の POSIX shm 9 シンボル（1ファイル）で、下流4クレートのエラーはすべてその連鎖と確定。shm を stub 化すると `native-wgpu-renderer` と `native-overlay`（6,628行のnapi addon）は**無改造で型検査通過**、残るのは `rust-backend` の `cfg(unix)` 掛け漏れ5箇所のみ。macOS専用 stub は全経路に既設でコンパイルを妨げていなかった（仮説H-1棄却）。リンク・実行時は未検証（2026-08-22）
