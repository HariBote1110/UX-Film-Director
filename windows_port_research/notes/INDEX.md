# Windows 移植研究ノート索引

macOS-first（ADR-001）で作った現行実装を Windows へ運ぶ道筋を、印象ではなく実測で
詰める研究。新しいものを上に置く。1行1ノート。

- [electron-real-app-on-windows.md](electron-real-app-on-windows.md) — **Electron 実物で検証**。Rust側を一切ビルドせず `npm install`→`npx tsc`→`npx vite build`→`npx electron .` でアプリが Windows で起動しUIも描画（準対応MVPの「ビルド」「起動」を達成）。overlay は実物の Chromium ウィンドウの上でも per-pixel alpha で正しく合成され、ちらつき・z-order競合は観測されず。クリックは `Chrome_RenderWidgetHostHWND` に素通り。起動ログの `DXC create compiler failed` は**無害**で WebGPU は動く（nvidia/ampere、adapter/device とも取得可）——ただし `navigator.gpu` は secure context でしか生えないので `data:` URL で測ると誤判定する。`npm run build` は POSIX形式のenv代入のため Windows で動かない（2026-08-22）
- [dcomp-crosswindow-and-hittest.md](dcomp-crosswindow-and-hittest.md) — **別ウィンドウ間の透過合成とクリック透過を実機確認**。オーナー付き `WS_POPUP`+`WS_EX_NOREDIRECTIONBITMAP` の overlay が、別ウィンドウである親の内容の上に per-pixel alpha で正しく合成された（画面キャプチャで数値・画像とも一致）。クリック透過は **`WS_EX_TRANSPARENT` だけでは抜けず**、`WM_NCHITTEST` に `HTTRANSPARENT` を返して初めて `WindowFromPoint` が下のウィンドウを返す（macOS の `hitTest:` nil と同じ対処）。macOS の Bug E（wgpu が layer を差し替えるので opaque 再適用が要る）に相当する問題は Windows には無い。RDPで接続しセッションをActiveにすると画面キャプチャが機能する。**Chromium 実物との組み合わせは未検証**（2026-08-22）
- [dcomp-transparent-composite-visual.md](dcomp-transparent-composite-visual.md) — **透過合成の目視確認に成功**。Windows実機で wgpu 30 の composition swapchain に premultiplied alpha で描いた内容が DirectComposition で正しく合成された（完全透明部は下の市松がそのまま、50%部は `src + dst*(1-a)` どおりの (128,128,127)）。macOS の CAMetalLayer + setOpaque:NO + 透明clear と同じ構成が DirectComposition + alpha_mode:PreMultiplied でそのまま成立し、退避策は全て不要と確定。z順は `AddVisual` の参照visualを明示しないと逆転する。切断RDPセッションでは画面キャプチャが全面黒になるため `PrintWindow(PW_RENDERFULLCONTENT)` を使う。**別ウィンドウ間の合成（Electron/Chromium の上に乗せる形）は未確認**（2026-08-22）
- [dx12-alpha-real-hardware.md](dx12-alpha-real-hardware.md) — Windows実機（mainpc / RTX 3070 Ti）で透過を実測。現行 wgpu 0.20 は実機でも `ALPHA_MODES=[Opaque]` で PreMultiplied は configure 失敗（前ノートの読解を追認）。**しかし wgpu 30 では同じ機械・同じ IDCompositionVisual で `[Auto, Inherit, Opaque, PostMultiplied, PreMultiplied]` となり PreMultiplied が通った** ——修正は **wgpu-hal 25.0.2** から入っており、透過不可はプラットフォーム制約ではなく wgpu のバージョン問題と確定（仮説H-2棄却）。wgpu-hal パッチも自前 swapchain も不要。ただし透過が効くのは composition 系 target のみで素の HWND は 30 でも Opaque。SSH 直実行では DirectComposition が E_ACCESSDENIED になるため `schtasks /it` 経由で実行する必要がある（2026-08-22）
- [cametallayer-equivalent-and-alpha.md](cametallayer-equivalent-and-alpha.md) — CAMetalLayer の Windows 相当は IDCompositionVisual で、wgpu 0.20 に `SurfaceTargetUnsafe::CompositionVisual` の入口も既にある（仮説H-2棄却）。**ただし wgpu-hal の dx12 backend が `composite_alpha_modes` を Opaque のみ広告し `map_acomposite_alpha_mode` が `DXGI_ALPHA_MODE_IGNORE` を直返しするため、wgpu 経由では透過 overlay が作れない**（wgpu-hal 24.0.4 でも同様＝バージョン上げでは直らない）。しかも `choose_live_surface_alpha_mode` が Opaque へ黙って fallback するのでエラーにならず無言の見た目バグになる。overlay surface の入口 `from_appkit_view` は macOS 専用、`from_surface` は cfg なしで再利用可能（2026-08-22）
- [current-portability-audit.md](current-portability-audit.md) — `cargo check --target x86_64-pc-windows-msvc` による現状棚卸し。唯一のビルドブロッカーは `shared-memory-spike` の POSIX shm 9 シンボル（1ファイル）で、下流4クレートのエラーはすべてその連鎖と確定。shm を stub 化すると `native-wgpu-renderer` と `native-overlay`（6,628行のnapi addon）は**無改造で型検査通過**、残るのは `rust-backend` の `cfg(unix)` 掛け漏れ5箇所のみ。macOS専用 stub は全経路に既設でコンパイルを妨げていなかった（仮説H-1棄却）。リンク・実行時は未検証（2026-08-22）
