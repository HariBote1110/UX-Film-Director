# テキスト影のぼかし（textShadow.blur）未実装バグの修正

## 決定
- `rust-backend/src/generated/text.rs` の `paint_buffer` は `_blur: f32` を受け取るだけで
  一切使っておらず、`textShadow.blur` が常に無視されていた（影は常にシャープなオフセットコピー）。
- 影の描画だけを新設の `paint_shadow` に分離した。`blur <= 0`（または計算上ブラー半径が0になる
  ほど小さい値）は従来どおり `paint_buffer` で即座にシャープ描画し、回帰させない。
- `blur > 0` のときは、影グリフをまずローカルなアルファバッファ（影のバウンディングボックス＋
  ブラーの広がり分だけ）へラスタライズし、分離可能ボックスブラー3パス（水平＋垂直を1セットとして
  3セット）でガウシアンを近似してから `blend_pixel` で合成する。色・アルファの合成規則自体は
  変えていない。
- ブラー半径は CSS の `text-shadow`/`box-shadow` の慣習に合わせ `σ = blur / 2` とし、
  Kutskir の定番式 `w = floor(σ * 3 * sqrt(2π) / 4 + 0.5)` でボックス幅を求め、
  `radius = floor(w / 2)` とした（`box_blur_radius_for` 関数、根拠はコード内コメントに記載）。
- パフォーマンス: プレーン全体ではなく、影のバウンディングボックス＋ブラー半径3倍
  （3パス直列適用で広がりが約3倍になるため）の範囲だけをアルファバッファとして確保・処理する。

## Alternatives considered
- 真のガウシアン畳み込み（カーネルを直接畳み込む）は実装・パフォーマンス面でボックスブラー3パス
  近似より重く、視覚的な差もほぼ無いため採用しなかった。
- プレーン全体をアルファバッファ化して毎回ぼかす案は、テキストが通常プレーンの一部にしか
  広がらないため無駄が大きく、バウンディングボックス限定処理を採用した。

## 検証で分かったこと（何が担保され、何が担保されていないか）

- **ぼかしが実際に効いていることを担保するのは Rust 側の4本の契約テスト**
  （`generated_frame_tests.rs`）。「ぼかし無しでは透明だった位置に影が現れる」
  「中心のアルファが下がる」「blurを大きくすると広がりが単調に増える」を画素で検証している。
- **重量E2Eはぼかしの証拠にならない。** 修正後のrunは総合PASS・settled・エラー0件・
  書き出し成功で**回帰が無いこと**は示すが、`screenshotInspection.colourfulPixelCount` は
  ぼかし導入前から 20192〜21908 の幅で揺れており（導入後は21960）、
  この指標の変化をぼかしの効果と読んではいけない。

## Constraints / Gotchas
- ぼかしはプレーン境界でクリップされる（既存の境界チェックと同じ扱い）。ぼかしによって影が
  従来より外側へ広がるため、大きな `blur` 値では境界での見切れが目立つ可能性がある。これは
  「テキストのバウンディングボックスに stroke/shadow の広がりが加算されていない」という
  既知の別バグであり、本修正では対応していない（コード内コメントにも明記）。
- `cargo test`（並列実行）で `tests/decode_control_plane.rs` の一部テストが稀に落ちることを
  確認したが、`--test-threads=1` では全テストが通過し、修正前のコードでも同様に再現する
  （AVFoundation の並行デコードセッション周りの既存のflakiness）。テキスト描画とは無関係。

## 追補（Beta-483b）: ブラー半径の上限クランプ

レビューで、ボックスブラーに**半径の上限が無い**脆弱性が見つかり修正した。

- `box_blur_horizontal` / `box_blur_vertical` の初期窓和ループ `for x in 0..=radius` は
  バッファ幅と無関係に `radius + 1` 回まわる（`if (x as usize) < width` は加算を
  スキップするだけでループ自体は回る）。`blur: 1e9` では半径が約4.7億になり、
  **10秒でも終わらない**ことを実測した。影付きテキストのフレーム生成は再生・書き出しで
  毎フレーム走るため影響が大きい。
- `window = 2 * radius + 1` は radius が `i32::MAX / 2` を超えると**オーバーフロー**する
  （debugビルドではpanic）。
- `blur` は `PropertyPanel` の数値入力由来だが `max` 属性が無く、プロジェクトファイルを
  直接編集・インポートすれば任意値が入りうる。**Rust側で防ぐのが本筋**と判断した。

修正: `clamp_box_blur_radius(radius, width, height)` を新設し `max(width, height)` で
クランプする。バッファより大きい半径でぼかしても結果は「全体に拡散しきった状態」以上には
変わらないため、**通常のblur値では半径が1も変わらず見た目に影響しない**。
`window` は `i64` で計算し、NaN / ±Infinity はぼかし無しへフォールバックする。

### 実装中に判明した境界の性質

クランプ上限付近（`radius >= width`）では、ボックスブラーの平均計算がバッファ外の
暗黙のゼロパディングを含むため、**影の総アルファが急激に0へ希釈される**
（実測: radius 300 で約4万ピクセル着色、radius 400 で0）。これはゼロパディング
ブラーの数学的に正しい挙動（エネルギーが広い面積へ拡散するのでピークが下がる）であり、
極端値でのみ発現する。契約テストは「ハングもpanicもせず寸法の壊れていない有限のフレームが
返ること」に絞り、影の可視性そのものは要求しない形にした。
